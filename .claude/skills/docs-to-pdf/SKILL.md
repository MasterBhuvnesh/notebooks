# Docs to PDF

## Overview

**One book, one folder.** Every document in this repo lives in its own directory under
`docs/`, named after the book in kebab-case with no date prefix: `docs/rabbitmq`,
`docs/kafka`, `docs/redis`. The folder holds `main.tex` and the mermaid sources; everything
else in it is generated by `tools/build.py`. Never write a document into `docs/` directly,
and never put two books in one folder.

Create the folder with the scaffold command, not by hand - it lays down `main.tex` and both
`diagrams/` subfolders in one step:

```
python tools/build.py --new <book-name>
```

**Core principle:** mermaid never reaches LaTeX. It is rendered to PNG out of band, and the
`.mmd` sources stay on disk in `diagrams/mmd/` so diagrams can be edited later.

**Never replace a diagram with ASCII art.** It looks like a solution and is not one - the
user asked for their diagram, and the build renders it for you.

**The look is not yours to choose.** It lives in `shared/notebooks.sty`: blue `accent`
(#1F5FA9) for section titles, hyperlinks and table headers; teal `accent2` (#0E7C66) for
`\field` labels and filename headings; pale `rulecol` for the rule under a section title.
Headings are coloured and a size larger, never bold. A document **never** defines a colour,
a heading format, or a listing style. If the user wants the palette changed, change it in
the `.sty` - where it changes for every document at once.

**The worked example is in the repo:** `docs/rabbitmq/main.tex` - a 29-page
document, 14 sections, 9 diagrams, using the optional one-page-per-topic layout. Read it
for the shape of real sections, tables and listings, and for how little preamble a document
needs.

## When to Use

- "Add a document about X to notebooks"
- "Make a PDF of these docs / this tutorial / this README"
- Source has fenced code blocks, ```mermaid blocks, or reference tables

**Not for:** slide decks (use Beamer), single-page CVs, or anything the user wants as a
live web page.

## Workflow

1. **Read the whole source first.** Count the sections, code blocks and diagrams, so
   nothing is silently dropped.
2. **Create the book's folder:** `python tools/build.py --new <book-name>`. This creates
   `docs/<book-name>/main.tex` and the `diagrams/mmd` + `diagrams/png` pair. The name is
   the subject in kebab-case with no date prefix (`rabbitmq`, `docker-networking`), matching
   the existing directories. This step is not optional: a document without its own folder
   has nowhere for its diagrams and will not be picked up by the build.
3. **Extract every ```mermaid block** to `docs/<book-name>/diagrams/mmd/NN-name.mmd`,
   numbered in document order. These files are part of the deliverable - never delete them after
   rendering, and never write into `diagrams/png/` by hand.
4. **Write `main.tex`.** The preamble is three lines plus metadata; see below.
5. **Build:** `python tools/build.py <book-name>`. It renders the diagrams, compiles twice,
   and fails on any LaTeX error or `Overfull \vbox`.
6. **Verify by reading the PDF**, not the log (see Verification).

## The document skeleton

```latex
\documentclass[11pt,a4paper]{article}
\usepackage{notebooks}

\notebooktitle{AMQP Complete Guide}
\notebooksubtitle{Messaging with RabbitMQ}
\notebooktagline{One page of theory, one page of code, per topic.}
\notebookauthor{bhuvii}
\notebooksource{github.com/MasterBhuvnesh/notebooks}

\begin{document}
\notebookcover          % title page + table of contents

\section{First topic}
...
\end{document}
```

Only `\notebooktitle` is required; the others vanish from the cover when unset. It also
feeds the PDF metadata, the running header, and the repo's README index - so it is the one
line that must be right.

From the style, available everywhere: `\mmd`, `\field`, `\notebookcover`, the `js`/`py`/`sh`
listing environments, `\hlerror` / `\hlinfo` / `\hlwarning`, and the `accent` / `accent2` /
`tablehead` colours.

## Page layout

**Default: let the content flow.** Sections run one after another, `\newpage` only where a
break genuinely helps. Do not impose a page structure the user did not ask for.

The rest of this section describes an **optional** layout - **one topic is one theory page
plus one code page** - so the reader sees the idea on the left of a spread and the code on
the right. Use it only when the user asks for something like "theory on one page, code on
the next". It suits tutorials with a repeating shape (a pattern, its diagram, its two code
files) and fights any document without one.

```latex
\section{Work Queues}          % theory page starts

\field{Short description:}{One or two sentences, what it is.}
\field{Theory:}{The idea behind it.}
\field{How it works:}{The mechanics, in order.}
\field{Use case example:}{A concrete situation the reader recognises.}

\subsection{Architecture diagram}
\mmd{02-work-queues.png}

\subsection*{Key Points}       % starred: stays out of the TOC
\subsection*{Notes}

\newpage                       % code page starts
\subsection{Code examples}
\subsubsection*{Producer (\texttt{send.js})}
```

- **Numbered vs starred.** `\subsection{Architecture diagram}` and `\subsection{Code
  examples}` are numbered so they appear in the table of contents and give it the
  two-line-per-topic rhythm. `Key Points` and `Notes` are starred so they do not.

The rest holds whatever the layout:

- **When a field is really a list**, give `\field` an empty or one-line second argument and
  follow it with an `itemize`. Do not bury a three-item list inside a paragraph.
- **Page budget**, when a page does have to hold a fixed amount: roughly 50 lines of
  `\footnotesize` code, or 65 of `\scriptsize`. Over budget, shrink the listing with
  `\begin{js}[basicstyle=\ttfamily\scriptsize]` before you trim the code.
- **A section that spills** by a line or two is nearly always the diagram. Cap it:
  `\mmd[0.30]{...}`.
- **Reference tables** (`tabularx` + `booktabs` + `\rowcolor{tablehead}`) belong on their own
  page or at the end of a theory page, never wedged between two listings.
- **Filenames in headings** go in `\texttt{}` with `_` escaped: `\texttt{send\_log.js}`.

## Building

```
python tools/build.py <book-name>   # one document
python tools/build.py              # all of them, changed ones only
python tools/build.py --force      # ignore the hash cache
```

Never run `pdflatex` or `mermaid-cli` by hand - CI runs this same script, so a document
that only builds through your own ad-hoc command will fail there. What the script does,
so the knowledge is not lost:

- `npx @mermaid-js/mermaid-cli -i … -o … -b white -s 3 -p <config>` per changed `.mmd`.
  `-s 3` renders at 3× so text stays sharp at print DPI; `-b white` avoids a transparent
  background that turns grey in some viewers. The puppeteer config is **generated** from
  `PUPPETEER_EXECUTABLE_PATH` or a detected browser - a committed `executablePath` is wrong
  on every machine but the one that wrote it.
- `pdflatex -interaction=nonstopmode -halt-on-error main.tex`, **twice**: the first pass
  writes `.aux` and `.toc`, the second reads them back so the table of contents, page
  references and internal links resolve. `TEXINPUTS` points at `shared/` so
  `\usepackage{notebooks}` resolves.
- Then it greps the log the way you would: `^!` for real errors, `Overfull \vbox` (content
  running off the bottom of a page) which must be zero, and
  `Output written on main.pdf (N pages, M bytes)` for the verdict.

Byproducts (`.aux`, `.log`, `.toc`, `.out`) are gitignored and safe to delete.

## Diagrams: mermaid to PNG

Write the `.mmd` into `docs/<book-name>/diagrams/mmd/NN-name.mmd` and reference the render as
`\mmd{NN-name.png}` - the macro already prefixes `diagrams/png/`. The build renders changed
sources only (sha256 per file) and deletes a PNG when its own `.mmd` disappears.

**A document with no diagrams needs nothing extra**: no `.mmd` files, no `\mmd` calls. The
render step is skipped entirely.

**An image that is not a diagram** - a screenshot, a logo - goes straight into
`diagrams/png/` and is used with the same `\mmd{shot.png}`. The build leaves any PNG it did
not generate alone, so a hand-added image is safe there.

**Source mermaid is often invalid.** Markdown viewers are lenient; mermaid-cli is not.
`participant Q1 (*.nyse.*)` fails - a label with parens needs an alias:

```
participant Q1 as queue (*.nyse.*)
```

Fix it in the `.mmd`, rebuild, then **tell the user you changed their diagram source.**

**If the build reports no browser**, install Chrome/Chromium or set
`PUPPETEER_EXECUTABLE_PATH`. Do not download puppeteer's own browser (~100 MB) when one is
already on the machine.

## Markdown to LaTeX conversion

| Markdown | LaTeX |
|---|---|
| `# H1` / `## H2` / `### H3` | `\section` / `\subsection` / `\subsubsection` |
| unnumbered heading | `\section*{…}` + `\addcontentsline{toc}{section}{…}` |
| ```` ```python ```` | `\begin{py} … \end{py}` |
| `**Use case:** foo` | `\field{Use case:}{foo}` (label picks up `accent2`) |
| pipe table | `tabularx` + `booktabs` |
| `[text](url)` | `\href{url}{text}` |
| `--` in prose | `--` renders as an en dash; that is usually what you want |

**Escape LaTeX specials in prose:** `# $ % & _ { } ~ ^ \`. `_` inside identifiers
(`routing_key`, `basic_ack`) is the one that bites. `\texttt{}` does **not** make `_` safe -
escape it as `\_`, or use `\lstinline|routing_key|`. Text *inside* a listing environment
needs no escaping at all; that is the whole point of it.

## Inline highlights

`\hlerror`, `\hlinfo`, `\hlwarning` are defined in the style. Use them for a recurring term
instead of yet another `\texttt{}`:

```latex
\field{Use case example:}{A log aggregator where services emit severity levels. Only the
\hlerror\ logs page the on-call engineer, while \hlinfo\ and \hlwarning\ logs go to storage.}
```

- **The gotcha that will bite:** LaTeX eats the space after a macro name. `\hlerror logs`
  prints "errorlogs". Write `\hlerror\ logs` (backslash then space) or `\hlerror{} logs`.
  No trailing backslash before punctuation: `\hlinfo.` is fine.
- `\colorbox` will not line-break inside the box, so highlight single words, never a phrase
  that might straddle a line ending.
- Highlights do **not** work inside a `listings` environment. To highlight in code, use
  `escapeinside={(*}{*)}` in `\lstset` and write `(*\hlerror*)` in the listing.
- Need a new one? Add it to `shared/notebooks.sty`, not to the document.

## Gotchas

| Symptom | Cause | Fix |
|---|---|---|
| `File notebooks.sty not found` | ran `pdflatex` by hand | use `python tools/build.py`; it sets `TEXINPUTS` |
| `! Missing $ inserted` | a bare `_` in prose or a heading | `\_` |
| `Unicode character ✓ not set up` | raw UTF-8 in a listing | add it to `literate=` in the `.sty`; only map glyphs actually present |
| Build fails on `Overfull \vbox` | content off the bottom of a page | cap the diagram `\mmd[0.30]{...}`, or shrink the listing |
| Wide code overflows the margin | - | already handled: `breaklines=true` in the style |
| Image not found | wrote `\mmd{diagrams/png/x.png}` | the macro adds the prefix: `\mmd{x.png}` |
| TOC empty or page refs wrong | one compile pass | the script always runs two; do not shortcut it |
| Macro output runs into the next word | LaTeX eats the space after a macro name | `\hlerror\ logs`, not `\hlerror logs` |

## Verification

The build saying "OK" proves the checks passed, not that the document is right.

**1. If the user asked for a fixed page structure, check it from `main.toc`.** Cheaper than
opening every page, and it is what catches a diagram or a listing quietly pushing a topic
onto an extra page. Under one-page-per-topic, each topic's section entry and its "Code
examples" entry must differ by exactly 1:

```
\contentsline {section}{\numberline {9}Queue Types}{18}{section.9}%
\contentsline {subsection}{\numberline {9.1}Code examples}{19}{subsection.9.1}%
```

Parse the `\contentsline` lines, pair each section with its next "Code examples", and assert
every gap is 1. A gap of 2 means the theory page spilled; the next section starting 2 after
the code page means the listings spilled.

**2. Read the actual PDF pages** - at minimum the title page, one page holding an embedded
diagram, and one holding a long code block. Confirm the diagram rendered legibly, the code
did not run off the page, and the page is not two thirds empty.

**3. Check the generated `CHANGELOG.md` and the README index row** exist and name the
document correctly. A wrong `\notebooktitle` shows up in three places at once.

Then report the page count and byte size.

## Common Mistakes

- Converting mermaid to ASCII art because "LaTeX cannot render mermaid" - the build renders it.
- Deleting the `.mmd` files after rendering, or writing a PNG into `diagrams/png/` by hand.
- Putting a colour, a `\titleformat`, or an `\lstset` in a document instead of the `.sty`.
- Running `pdflatex` directly, then reporting done - CI runs `tools/build.py` and will differ.
- Claiming success off the build output without opening the PDF.
- Editing `CHANGELOG.md`, `.build.json` or the README index table - all three are regenerated.
- Imposing the one-page-per-topic layout on a document whose author never asked for it.
- Cutting content to make a page fit before trying `basicstyle=\ttfamily\scriptsize`.
