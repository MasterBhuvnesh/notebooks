\section{Introduction to Servers}

\field{Short description:}{A server is a computer or software system that provides services,
resources, or data to other computers, called clients, over a network.}

\field{Everyday examples:}{}

\begin{itemize}\itemsep2pt
  \item Opening a website: the browser sends a request to a \textbf{web server}.
  \item Checking Gmail: a \textbf{mail server} delivers the messages.
  \item Using online banking: a \textbf{database server} stores and retrieves the account.
\end{itemize}

\field{What a server does:}{Stores files, hosts websites, manages databases, runs
applications, sends and receives email, shares printers and other resources, and manages
users and security.}

\section{The Traditional Server Model}

\field{Short description:}{Before virtualization and cloud computing, organizations
typically deployed \textbf{one physical server for one application}. Each application had
its own dedicated hardware.}

\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\rowcolor{tablehead} \textbf{Application} & \textbf{Physical server} \\
\midrule
Website & Server 1 \\
Database & Server 2 \\
Email & Server 3 \\
ERP & Server 4 \\
\bottomrule
\end{tabularx}

\subsection{Advantages}

\begin{itemize}\itemsep3pt
  \item \textbf{High performance.} Applications have direct access to hardware resources.
  \item \textbf{Better security.} Each application runs on its own physical machine.
  \item \textbf{Reliability.} No interference from other applications sharing the hardware.
  \item \textbf{Simple architecture.} Easy to install, configure and troubleshoot.
  \item \textbf{Full hardware control.} Administrators control the server hardware completely.
\end{itemize}

\subsection{Disadvantages}

\begin{itemize}\itemsep3pt
  \item \textbf{Low resource utilization.} Most servers use only 10--20\% of CPU and memory,
        leaving the rest idle.
  \item \textbf{High cost.} Each application requires separate hardware.
  \item \textbf{High power consumption.} More servers draw more electricity and need more
        cooling.
  \item \textbf{More physical space.} Multiple servers occupy valuable rack space.
  \item \textbf{Difficult scalability.} A new application often means buying new hardware.
  \item \textbf{Higher maintenance.} Every server needs updates, monitoring, backups and
        repairs.
  \item \textbf{Single point of failure.} If a physical server fails, its application becomes
        unavailable.
\end{itemize}

\subsection*{Why a new technology was needed}

As organizations expanded they faced too many physical servers, rising hardware costs,
increased electricity and cooling expenses, underutilized resources, complex management, and
slow deployment of new services. These limitations led to \textbf{virtualization}, which
allows multiple virtual servers to run on a single physical machine, and virtualization in
turn became the foundation for \textbf{cloud computing}.

\section{Introduction to Virtualization}

\field{Short description:}{Virtualization is a methodology for dividing computer resources
into more than one execution environment, applying concepts such as partitioning,
time-sharing, machine simulation and emulation.}

\field{Theory:}{Virtualization is a method in which multiple independent operating systems
run on one physical computer. It maximizes the usage of available physical resources, so one
can achieve high server usage: it increases total computing power while decreasing overhead.
Increasing the number of logical operating systems on a single host reduces hardware
acquisition and maintenance cost for an organization.}

\field{How it works:}{The architecture has three layers. Layer 1 is the physical
infrastructure of servers, networks and storage. Layer 2 is the virtual infrastructure,
consisting of hypervisors, virtual infrastructure services and automated solutions that
optimize the IT process. Layer 3 holds the virtual machines, where different operating
systems and applications are deployed. A single virtual infrastructure supports more than one
virtual machine, so the physical resources of the whole infrastructure are shared across many
virtual machines for maximum efficiency.}

\subsection*{Notes}

\begin{itemize}\itemsep2pt
  \item Virtualization is a trend in IT that includes autonomic computing and utility
        computing: the environment manages itself, and every resource is seen as a utility
        that a client pays per use.
  \item It reduces the burden of workloads on users by centralizing administrative tasks and
        improving scalability.
\end{itemize}

\subsection{Reasons for using virtualization}

\begin{itemize}\itemsep3pt
  \item Virtual machines consolidate the workloads of under-utilized servers, saving on
        hardware, environmental costs and management.
  \item Legacy applications can keep running inside a VM.
  \item A VM provides a secure sandbox for running an untrusted application.
  \item A VM helps in building a secured computing platform.
  \item A VM provides an illusion of hardware.
  \item A VM simulates networks of independent computers.
  \item A VM supports running distinct operating systems with different versions.
\end{itemize}

\section{Hypervisor}

\field{Short description:}{A hypervisor, or Virtual Machine Monitor (VMM), is software that
lets multiple operating systems run on a single physical machine.}

\field{Theory:}{It manages hardware resources such as CPU, memory and storage and allocates
them to virtual machines without interference. This improves hardware utilization, reduces
costs, and provides flexibility in cloud and server environments.}

\field{How it works:}{A hypervisor runs on hardware or on a host OS to create and manage
virtual machines, each with its own virtual CPU, memory, storage and network. It intercepts
guest OS requests and translates them to physical hardware, ensuring isolation, security and
stability.}

\subsection{Architecture diagram}
\mmd[0.34]{02-hypervisor-how-it-works.png}

\subsection{Type 1 hypervisor}

A Type 1 hypervisor runs directly on the host's hardware and does not rely on a host
operating system. This architecture offers better performance and security because there is
no intermediary OS. It is the standard for enterprise-level data centres and for cloud
providers such as Amazon Web Services and Microsoft Azure.

\field{Examples:}{VMware ESXi, Microsoft Hyper-V, KVM (Kernel-based Virtual Machine), Xen.}

\begin{itemize}\itemsep2pt
  \item \textbf{Pros:} high performance through direct hardware access; strong security with
        no intermediate OS layer; suitable for mission-critical workloads.
  \item \textbf{Cons:} requires dedicated hardware; setup and management are complex compared
        to Type 2.
\end{itemize}

\subsection{Type 2 hypervisor}

A Type 2 hypervisor runs on top of a conventional operating system such as Windows, macOS or
Linux. It is essentially an application within the host OS. This type is generally used for
desktop virtualization, development and testing, where a user needs to run multiple operating
systems on a personal computer. Performance is slightly lower than Type 1 because of the
overhead of the host OS.

\field{Examples:}{Oracle VM VirtualBox, VMware Workstation, Parallels Desktop.}

\begin{itemize}\itemsep2pt
  \item \textbf{Pros:} easy to install and use; useful for development, testing and malware
        analysis; good host--guest integration features.
  \item \textbf{Cons:} slower performance with no direct hardware access; security depends on
        the host OS, so a compromise of the host may affect the guests.
\end{itemize}

\section{Full Virtualization}

\field{Short description:}{Full virtualization was introduced by IBM in 1966. It was the
first software solution for server virtualization and uses binary translation together with
direct execution.}

\field{How it works:}{The virtual machine completely isolates the guest OS from the
virtualization layer and the hardware. Kernel code is translated to replace non-virtualizable
instructions with new sequences of instructions that have the intended effect on the virtual
hardware, while user level code is executed directly on the processor for high performance.}

\field{Examples:}{Microsoft and Parallels systems.}

\subsection{Architecture diagram}
\mmd[0.30]{04-full-virtualization.png}

\section{Paravirtualization}

\field{Short description:}{Paravirtualization is the category of CPU virtualization that uses
hypercalls for operations handled at compile time.}

\field{How it works:}{The guest OS is not completely isolated, only partially isolated by the
virtual machine from the virtualization layer and hardware. The OS kernel is modified to
replace non-virtualizable instructions with hypercalls that communicate directly with the
virtualization layer, which improves performance and efficiency.}

\field{Examples:}{VMware and Xen.}

\newpage
\section{Hardware Based Virtualization}

\field{Short description:}{Hardware vendors added CPU features that simplify virtualization
directly in silicon.}

\field{How it works:}{First generation enhancements include Intel Virtualization Technology
(VT-x) and AMD's AMD-V. Both target privileged instructions with a new CPU execution mode that
allows the VMM to run in a root mode below ring 0. Privileged and sensitive calls are set to
trap automatically to the hypervisor, removing the need for either binary translation or
paravirtualization. The guest state is stored in Virtual Machine Control Structures (VT-x) or
Virtual Machine Control Blocks (AMD-V).}

Virtualizing the server infrastructure, so no further physical servers are needed for

Widely used in datacentres with large storage. It helps create, delete and allocate storage

\subsection{Operating system level virtualization}

An abstraction layer between the traditional OS and user applications. OS-level virtualization
creates isolated \textbf{containers} on a single physical server, using one OS instance to
utilize the hardware and software in data centres. The containers behave like real servers. It
is commonly used to create virtual hosting environments that allocate hardware resources among
a large number of mutually distrusting users, and to a lesser extent to consolidate server
hardware by moving services on separate hosts into containers or VMs on one server.

The technology isolates applications from the underlying operating system and from other
applications, to increase compatibility and manageability. Docker can be used for this

\newpage
\subsection{Instruction set architecture level}

\begin{itemize}\itemsep2pt
  \item Virtualization is performed by emulating a given ISA with the ISA of the host machine.
  \item For example, MIPS binary code can run on an x86-based host machine through ISA
        emulation.
  \item It becomes possible to run a large amount of legacy binary code written for various
        processors on any given new hardware host.
\end{itemize}

\subsection{Hardware abstraction level}

\begin{itemize}\itemsep2pt
  \item Hardware-level virtualization is performed right on top of the bare hardware. It
        generates a virtual hardware environment for a VM, and the process manages the
        underlying hardware through virtualization.
  \item The idea is to virtualize a computer's resources, such as its processors, memory and
        I/O devices, to upgrade the hardware utilization rate by multiple concurrent users.
  \item It was implemented in the IBM VM/370 in the 1960s. More recently the Xen hypervisor
        has been applied to virtualize x86-based machines running Linux or other guest OS
        applications.
\end{itemize}

\subsection{Operating system level}

\begin{itemize}\itemsep2pt
  \item An abstraction layer between the traditional OS and user applications.
  \item It creates isolated containers on a single physical server, with the OS instances
        utilizing the hardware and software in data centres.
  \item The containers behave like real servers, and are commonly used for virtual hosting
        environments allocating hardware among mutually distrusting users.
\end{itemize}

\subsection{Library support level}

\begin{itemize}\itemsep2pt
  \item Most applications use APIs exported by user-level libraries rather than lengthy system
        calls, so a well-documented API becomes another candidate for virtualization.
  \item Virtualization with library interfaces controls the communication link between
        applications and the rest of the system through API hooks.
  \item WINE implements this approach to support Windows applications on top of UNIX hosts.
  \item vCUDA allows applications executing within VMs to leverage GPU hardware acceleration.
\end{itemize}

\subsection{User-application level}

\begin{itemize}\itemsep2pt
  \item Virtualization at the application level virtualizes an application as a VM. On a
        traditional OS an application runs as a process, so this is also known as
        process-level virtualization.
  \item The most popular approach is to deploy high level language (HLL) VMs. The
        virtualization layer sits as an application program on top of the operating system and
        exports the abstraction of a VM that runs programs compiled to a particular abstract
        machine definition.
  \item The Microsoft .NET CLR and the Java Virtual Machine are two good examples.
\end{itemize}

\section{Containers}

\field{Short description:}{A container is an isolated, stand-alone unit that encapsulates an
application and all its dependencies. It runs consistently in any environment, independent of
the host system.}

\field{Theory:}{It is a light, executable software package that wraps everything an
application needs: libraries, configuration files and binaries. The application behaves the
same way on a developer's laptop, in a testing environment, or on a production server. Unlike
traditional virtual machines that carry a full OS, containers pack only what is required,
which makes them faster and more efficient.}

\field{How it works:}{Containerization is the process of packing an application together with
all its dependencies into a container so it runs consistently from one computing environment
to another. In simple terms it uses the host OS kernel to run many isolated instances of
applications on the same machine, which makes it very lightweight and efficient.}

\subsection{Containers versus virtual machines}

Both containers and VMs run applications in isolated environments, but they differ in
architecture, performance, resource usage and startup time.

\section{Container Orchestration}

\field{Short description:}{Container orchestration is the process of automating the
deployment, management, scaling and networking of containers throughout their lifecycle.}

\field{Theory:}{Orchestration platforms such as Kubernetes create a smooth, self-managing
operation and coordinate microservices held in separate containers. Kubernetes eliminates many
of the manual processes involved in deploying and scaling containerized applications, and Red
Hat creates essential tools for securing, simplifying and automatically updating container
infrastructure.}

\subsection{Why it is needed}

When many containers run across different machines, managing them manually becomes difficult.
An orchestration platform automates:

\begin{itemize}\itemsep3pt
  \item \textbf{Deployment:} starts and distributes containers across servers.
  \item \textbf{Scaling:} increases or decreases the number of container instances based on
        demand.
  \item \textbf{Load balancing:} distributes incoming traffic among healthy containers.
  \item \textbf{Self-healing:} restarts failed containers or moves them to healthy nodes.
  \item \textbf{Service discovery:} allows containers to find and communicate with each other.
  \item \textbf{Rolling updates and rollbacks:} updates applications with minimal downtime and
        reverts changes if needed.
  \item \textbf{Resource management:} efficiently allocates CPU, memory and storage.
\end{itemize}

\subsection*{Benefits}

Orchestration platforms automate the entire lifecycle of containers, transforming what would
be a non-stop maintenance operation for IT teams into a smooth, self-managing one, and bring
advantages in development methods, costs and security.

\section{Software Virtualization}

\field{Short description:}{Software virtualization is a technique that allows a server to run
multiple operating systems and applications by creating a virtual environment.}

\field{Theory:}{Software virtualization develops a virtual environment in which software,
applications and operating systems can be installed. A virtualized software is simply an
application that has been installed inside such an environment. It lets a user run more than
one operating system on the same machine. VMware and VirtualBox are common examples.}

\subsection{Components}

\begin{itemize}\itemsep3pt
  \item \textbf{Hypervisor:} a piece of software that manages and allocates hardware
        resources to the virtual machines.
  \item \textbf{Virtual machines:} independent computers, each running its own operating
        system on a portion of the physical machine's hardware.
  \item \textbf{Abstraction layer:} the layer of separation between the physical hardware and
        the virtual machines.
\end{itemize}

\subsection{Types of software virtualization}

The three forms studied in this unit are operating system virtualization, application
virtualization and service virtualization. Each is covered in its own section below.

\newpage
\section{Operating System Virtualization}

\field{Short description:}{A virtualization technique in which the virtualization software
runs on top of a host operating system and creates isolated environments called containers.}

\field{Theory:}{Multiple applications or services run independently on the same physical
hardware while sharing the underlying OS kernel. The virtualization layer creates an
abstraction between the hardware and the applications, which improves resource utilization and
isolation. Unlike traditional virtualization, which creates complete virtual machines,
OS-based virtualization shares the host kernel among the containers, so it is lighter and more
efficient.}

\field{How it works:}{The host operating system kernel manages the containers through
specialised features that control resource access and allocation. Each container operates as
an isolated environment with its own process space, network interfaces and file systems, while
sharing the underlying kernel. The kernel enforces limits on CPU time, memory usage, disk
space and network bandwidth for each container, so one container cannot affect the others and
no conflicts or security breaches arise between them.}

\subsection{Architecture diagram}
\mmd[0.40]{14-os-virtualization.png}

\subsection{Types of virtual disk}

\begin{itemize}\itemsep3pt
  \item \textbf{Private virtual disk:} dedicated to a single container. It keeps data and
        configuration across restarts, much like a local hard disk.
  \item \textbf{Shared virtual disk:} used by several containers at the same time. Changes go
        to a temporary cache that is cleared on restart, which gives every container the same
        baseline configuration.
\end{itemize}

\subsection{Advantages}

\begin{itemize}\itemsep3pt
  \item \textbf{Resource efficiency:} containers share the host kernel, so memory and storage
        overhead is lower than with full virtualization.
  \item \textbf{Fast startup:} a container starts quickly because no full OS boot is needed.
  \item \textbf{High density:} more containers fit on the same hardware than virtual machines.
  \item \textbf{Portability:} containers move easily between host systems.
\end{itemize}

\subsection{Disadvantages}

\begin{itemize}\itemsep3pt
  \item \textbf{OS dependency:} every container must use the same operating system as the host.
  \item \textbf{Security concerns:} a kernel vulnerability can affect all containers at once.
  \item \textbf{Limited isolation:} isolation is weaker than in hardware-based virtualization.
\end{itemize}

\section{Application Virtualization}

\field{Short description:}{Application virtualization is the ability to run an application in
an environment different from the one it was developed for.}

\field{Theory:}{It allows IT administrators to install applications on a server and then
deliver them remotely to users' computers. The experience of using a virtualized application
is the same as using an application installed on a physical machine.}

\field{How it works:}{The common approach is server based. An administrator installs the
applications once, either in the organisation's data centre or through a hosting service, and
then uses application virtualization software to deliver them to users' desktops and other
connected devices. The user accesses the application as if it were installed locally, and the
user's actions are conveyed back to the server to be executed. Application virtualization is
an integral part of digital workspaces and desktop virtualization.}

\subsection{Architecture diagram}
\mmd[0.34]{15-application-virtualization.png}

\subsection{Benefits}

\begin{itemize}\itemsep4pt
  \item \textbf{Simplified management:} the applications to be delivered are installed on a
        single server rather than on every user device, which makes installing software,
        updates and patches far easier for the IT team.
  \item \textbf{Scalability:} administrators can deploy virtual applications to every
        connected device regardless of its operating system or storage capacity. The
        organisation then spends less on hardware, because employees only need a basic
        computer to reach the applications they work with.
  \item \textbf{Security:} access to applications is controlled centrally, so licences are
        easy to revoke when a user no longer needs them. The application never has to be
        uninstalled from a user's device, because it stays resident but reachable only through
        its container. This central control matters most when a device is lost or stolen,
        since sensitive data can no longer be reached remotely.
\end{itemize}

\section{Service Virtualization}

\field{Short description:}{Service virtualization simulates the behaviour of software
services, APIs, databases or third-party applications.}

\field{Theory:}{It lets developers and testers build, integrate and test an application even
when the real service is unavailable, incomplete, expensive to access or difficult to
configure. In simple terms, it creates a virtual version of a dependent service that behaves
like the real one without requiring the actual system.}

\field{How it works:}{Instead of communicating with the actual service, the application talks
to the virtual service, which returns predefined or dynamically generated responses.}

\field{Examples:}{Typical simulated responses are payment successful, payment failed, user not
found, server timeout and invalid request.}

\newpage
\section{Hardware Virtualization}

\field{Short description:}{Hardware virtualization allows multiple virtual machines to run on
a single physical machine.}

\field{Theory:}{It creates a virtual version of a computer's hardware components: the CPU,
memory, storage and network. The resulting virtual environment, the virtual machine, acts like
a real computer and runs its own operating system and applications independently of the host
system.}

\field{How it works:}{A software layer called the hypervisor creates and manages the virtual
machines on a single physical server. The hypervisor allocates the server's resources, such as
CPU, memory and storage, to each VM, so several operating systems and applications run
independently on the same hardware.}

\subsection{Benefits}

\begin{itemize}\itemsep4pt
  \item \textbf{Improved resource utilization:} consolidating several workloads onto one
        physical server makes better use of the hardware, so fewer physical servers are
        needed and energy consumption and floor space both drop.
  \item \textbf{Cost savings:} fewer machines means savings on both capital expenditure,
        which is buying the servers, and operational expenditure, which is maintaining and
        powering them.
  \item \textbf{Flexibility and scalability:} virtual machines are easy to create, modify and
        move, which matters for a business that has to adapt quickly to changing workloads.
  \item \textbf{Isolation and security:} each VM operates in isolation, so malware or a system
        failure is contained within a single VM.
  \item \textbf{Simplified management:} centralised tools let administrators manage many
        virtual environments from one interface, which is especially useful when the
        infrastructure is spread across several locations.
\end{itemize}

\newpage
\section{Storage Virtualization}

\field{Short description:}{Storage virtualization brings several storage devices together into
a single entity, for better efficiency, security and management.}

\field{Theory:}{Storage virtualization is a newer concept under virtualization: storage
systems use it to gain functionality and features. A storage system is also called a storage
array, a disk array or a filer. It uses special hardware and software to provide fast and
reliable storage for computing and processing data, and it is designed to accommodate large
capacity together with data protection.}

\field{How it works:}{Multiple physical storage devices are combined into a single logical
storage pool by a virtualization layer. That layer manages allocation, maps logical volumes to
physical devices and handles every read and write transparently. Users and applications see a
single logical storage system, while the software manages the physical storage underneath and
improves utilization, scalability, performance and ease of management.}

\subsection{Types of storage virtualization}
\mmd[0.24]{17-storage-virtualization-types.png}

\begin{itemize}\itemsep3pt
  \item \textbf{Block level virtualization:} separates logical storage from physical storage
        at the block level, as in IBM SVC and EMC VPLEX.
  \item \textbf{File level virtualization:} abstracts the file system from the physical
        storage, as in NAS solutions such as NetApp.
  \item \textbf{Object based storage:} holds data as objects rather than as files or blocks,
        as in AWS S3 and Ceph.
\end{itemize}

\subsection{Benefits}

\begin{itemize}\itemsep3pt
  \item \textbf{Enhanced storage utilization:} aggregates different storage devices
        efficiently.
  \item \textbf{Scalability:} storage scales easily as requirements grow.
  \item \textbf{Savings:} hardware cost falls because existing resources are reused.
  \item \textbf{Very high availability:} redundancy and failover support are built in.
  \item \textbf{Improved performance:} workload is distributed dynamically across the storage.
  \item \textbf{Easier data migration:} data moves from one storage system to another
        seamlessly.
  \item \textbf{Energy efficiency:} optimised storage usage draws less power.
\end{itemize}

\section{The Data Center}

\field{Short description:}{A data centre is a centralised facility that houses computing
resources: servers, storage systems, networking equipment, power systems, cooling systems and
security infrastructure.}

\field{Theory:}{It is designed to store, process, manage and distribute large amounts of data
and applications continuously and securely. In simple terms, the data centre is the backbone
of modern IT infrastructure, providing the environment needed to run business applications,
websites, cloud services, databases and enterprise systems.}

\subsection{Need for a data centre}

\begin{itemize}\itemsep2pt
  \item Centralised storage and management of data
  \item High-speed data processing
  \item Secure storage of business information
  \item Continuous availability of services
  \item Disaster recovery and backup
  \item Support for cloud computing and virtualization
  \item Efficient resource utilization
\end{itemize}

\subsection{Objectives of a data centre}

\begin{itemize}\itemsep2pt

\subsection{Phase 1: Discovery}

Discovery is the process of collecting complete information about the existing IT

\begin{enumerate}\itemsep3pt

\section{Networking Concepts: Masks and CIDR}

\field{Short description:}{A mask is what separates the network identifier from the host
identifier in an IP address.}

\field{Theory:}{A mask is a 32-bit number made of a run of 1s followed by a run of 0s. It does
not apply to classes D and E. Classless interdomain routing, or CIDR, writes the mask in the
short form \texttt{/n}, where \texttt{n} is the number of 1 bits.}

\begin{tabularx}{\textwidth}{@{}llXl@{}}
\toprule
\rowcolor{tablehead}\textbf{CIDR} & \textbf{Dotted decimal} & \textbf{Binary} &
\textbf{Class} \\
\midrule
\texttt{/8} & \texttt{255.0.0.0} & \texttt{11111111 00000000 00000000 00000000} & A \\
\texttt{/16} & \texttt{255.255.0.0} & \texttt{11111111 11111111 00000000 00000000} & B \\
\texttt{/24} & \texttt{255.255.255.0} & \texttt{11111111 11111111 11111111 00000000} & C \\
\bottomrule
\end{tabularx}

\subsection*{Notes}

\begin{itemize}\itemsep2pt
  \item \textbf{Subnetting:} an organisation granted a large block in class A or B divides the
        addresses into several contiguous groups and assigns each group to a smaller network,
        called a subnet.
  \item \textbf{Supernetting:} an organisation combines several class C blocks to create a
        larger range of addresses. Several networks are combined into one supernetwork, or
        supernet.
\end{itemize}

\newpage
\section{Subnetting}

\field{Short description:}{Subnetting divides a large granted block into several smaller
networks, by borrowing bits from the host part and adding them to the network part.}

\field{Theory:}{Subnetting increases the number of 1s in the mask: a subnet mask has more 1s
than the corresponding default mask. To build a subnet mask, change some of the leftmost 0s in
the default mask to 1s. The number of subnets follows from the number of extra 1s: if there
are $n$ extra 1s there are $2^{n}$ subnets, and if $N$ subnets are needed the number of extra
1s is $\log_{2} N$. The number of subnets must therefore be a power of 2.}

\subsection{Levels of hierarchy}
\mmd[0.44]{22-subnet-hierarchy.png}

Without subnetting the address has two levels of hierarchy, network and host. With subnetting
it has three: network, subnet and host.

\subsection{Finding the subnetwork address}

The subnet address is found the same way as the network address, by applying the mask to the
address. There are two ways to do it.

\begin{itemize}\itemsep3pt
  \item \textbf{Straight method:} write both the address and the mask in binary and apply the
        AND operation.
  \item \textbf{Short-cut method:} if the byte in the mask is 255, copy the byte of the
        address. If the byte in the mask is 0, replace the byte of the address with 0. If the
        byte is neither 255 nor 0, write that byte of the mask and of the address in binary
        and AND them.
\end{itemize}

\subsection*{Example: straight method}

What is the subnetwork address if the destination address is \texttt{200.45.34.56} and the
subnet mask is \texttt{255.255.240.0}?

\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\rowcolor{tablehead}\textbf{Line} & \textbf{Binary} \\
\midrule
Address & \texttt{11001000 00101101 00100010 00111000} \\
Mask & \texttt{11111111 11111111 11110000 00000000} \\
Result & \texttt{11001000 00101101 00100000 00000000} \\
\bottomrule
\end{tabularx}

The subnetwork address is \texttt{200.45.32.0}.

\subsection*{Example: short-cut method}

What is the subnetwork address if the destination address is \texttt{19.30.84.5} and the mask
is \texttt{255.255.192.0}? The first two bytes of the mask are 255, so \texttt{19} and
\texttt{30} are copied. The last byte of the mask is 0, so \texttt{5} becomes \texttt{0}. The
third byte is neither, so AND it: \texttt{01010100} AND \texttt{11000000} is
\texttt{01000000}, which is 64. The subnetwork address is \texttt{19.30.64.0}.

\subsection*{Example: designing subnets in class C}

A company is granted the site address \texttt{201.70.64.0}, a class C address, and needs six
subnets.

The default mask of class C has 24 ones. Six is not a power of 2, and the next power of 2 is
$8 = 2^{3}$, so three more 1s are needed. The subnet mask has $24 + 3 = 27$ ones and
$32 - 27 = 5$ zeros, which is \texttt{11111111 11111111 11111111 11100000}, or
\texttt{255.255.255.224}. There are 8 subnets and each holds $2^{5} = 32$ addresses.

\subsection*{Example: designing subnets in class B}

A company is granted the site address \texttt{181.56.0.0}, a class B address, and needs 1000
subnets.

The default mask of class B has 16 ones. One thousand is not a power of 2, and the next power
of 2 is $1024 = 2^{10}$, so ten more 1s are needed. The subnet mask has $16 + 10 = 26$ ones
and $32 - 26 = 6$ zeros, which is \texttt{11111111 11111111 11111111 11000000}, or
\texttt{255.255.255.192}. There are 1024 subnets and each holds $2^{6} = 64$ addresses.

\section{Supernetting}

\field{Short description:}{Supernetting is the opposite of subnetting. Bits are borrowed from
the network side to combine a group of networks into one large supernetwork.}

\field{Theory:}{Demand for midsize blocks is high. Class A and class B addresses are almost
depleted, while class C addresses are still available but a block of 256 addresses is too
small for many organisations. In supernetting, several class C blocks are combined into a
larger range. This decreases the number of 1s in the mask: for four class C blocks the mask
changes from \texttt{/24} to \texttt{/22}. An organisation needing 1000 addresses can be
granted four contiguous class C blocks forming one supernetwork.}

\mmd[0.30]{23-supernetwork.png}

In subnetting, the first address of the subnet and the subnet mask define the range of
addresses. In supernetting, the first address of the supernet and the supernet mask define the
range.

\subsection*{Example: which packet belongs to the supernet}

A supernet has the first address \texttt{205.16.32.0} and the supernet mask
\texttt{255.255.248.0}. A router receives three packets, for \texttt{205.16.37.44},
\texttt{205.16.42.56} and \texttt{205.17.33.76}.

Applying the supernet mask gives \texttt{205.16.32.0}, \texttt{205.16.40.0} and
\texttt{205.17.32.0} respectively. Only the first address belongs to this supernet.

\subsection*{Example: valid sets of blocks}

A company needs 600 addresses. Which of these sets of class C blocks can form a supernet?

\begin{enumerate}\itemsep2pt
  \item \texttt{198.47.32.0}, \texttt{198.47.33.0}, \texttt{198.47.34.0}. No, there are only
        three blocks.
  \item \texttt{198.47.32.0}, \texttt{198.47.42.0}, \texttt{198.47.52.0}, \texttt{198.47.62.0}.
        No, the blocks are not contiguous.
  \item \texttt{198.47.31.0}, \texttt{198.47.32.0}, \texttt{198.47.33.0}, \texttt{198.47.52.0}.
        No, 31 in the first block is not divisible by 4.
  \item \texttt{198.47.32.0}, \texttt{198.47.33.0}, \texttt{198.47.34.0}, \texttt{198.47.35.0}.
        Yes, all three requirements are fulfilled.
\end{enumerate}

\subsection*{Example: the supernet mask for 16 blocks}

Sixteen blocks need four 1s of the default mask changed to 0s, so the mask is
\texttt{11111111 11111111 11110000 00000000}, or \texttt{255.255.240.0}.

\subsection*{Example: size and range of a supernet}

A supernet has the first address \texttt{205.16.32.0} and the supernet mask
\texttt{255.255.248.0}. The mask has 21 ones and the default mask has 24, so the difference of
3 gives $2^{3} = 8$ blocks. They run from \texttt{205.16.32.0} to \texttt{205.16.39.0}, so the
first address is \texttt{205.16.32.0} and the last is \texttt{205.16.39.255}.

\section{Classless Addressing}

\field{Short description:}{Classless addressing removes the classes altogether. Addresses are
still granted in blocks, but the size of a block varies with the nature and size of the
organisation.}

\field{Theory:}{Classless addressing was designed to overcome address depletion and give more
organisations access to the Internet. A household may be given only two addresses, while a
large organisation may be given thousands. It is referred to as classless interdomain routing,
or CIDR, and the block granted is called a CIDR block.}

\subsection{Rules for allocating a block}

\begin{enumerate}\itemsep3pt
  \item The IP addresses in the CIDR block must all be contiguous.
  \item The block size must be a power of 2, and the size of the block equals the number of IP
        addresses in it.
  \item The first IP address of the block must be divisible by the block size.
\end{enumerate}

For the beginning address, if the block has fewer than 256 addresses only the rightmost byte
has to be checked; if it has fewer than 65,536 addresses only the two rightmost bytes have to
be checked, and so on.

\subsection{Slash notation}

Slash notation, also called CIDR notation, is a shorter way of writing a subnet mask: instead
of the full mask, only the number of 1 bits is written after a slash. A block in classes A, B
and C is written \texttt{A.B.C.D/n}, where $n$ is 8, 16 or 24 respectively.

\subsection{Extracting information from an address}

Given any address in the block and the prefix length $n$, three facts follow.

\begin{enumerate}\itemsep3pt
  \item The number of addresses in the block is $N = 2^{32-n}$.
  \item The first address is found by keeping the $n$ leftmost bits and setting the $32 - n$
        rightmost bits to 0.
  \item The last address is found by keeping the $n$ leftmost bits and setting the $32 - n$
        rightmost bits to 1.
\end{enumerate}

\subsection{Address mask}

The address mask is a 32-bit number whose $n$ leftmost bits are 1 and whose remaining
$32 - n$ bits are 0. A computer finds it easily because it is the complement of $2^{32-n} - 1$.
Defined this way, the mask lets a program extract the block information with the bitwise NOT,
AND and OR operations.

\begin{enumerate}\itemsep2pt
  \item Number of addresses: $N = $ NOT(mask) $+ 1$.
  \item First address: (any address in the block) AND (mask).
  \item Last address: (any address in the block) OR NOT(mask).
\end{enumerate}

\subsection*{Example: range of a block}

A small organisation is given the block \texttt{205.16.37.24/29}. To find the last address,
keep the first 29 bits and change the last 3 bits to 1s.

\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\rowcolor{tablehead}\textbf{Line} & \textbf{Binary} \\
\midrule
Beginning & \texttt{11001111 00010000 00100101 00011000} \\
Ending & \texttt{11001111 00010000 00100101 00011111} \\
\bottomrule
\end{tabularx}

There are 8 addresses in the block. The same answer follows from the suffix length: it is
$32 - 29 = 3$, so there are $2^{3} = 8$ addresses, and if the first address is
\texttt{205.16.37.24} the last is \texttt{205.16.37.31}, because $24 + 7 = 31$.

\subsection*{Example: finding the network address}

What is the network address if one of the addresses is \texttt{167.199.170.82/27}?

The prefix length is 27, so keep the first 27 bits and change the remaining 5 to 0s. Those 5
bits fall in the last byte, which is \texttt{01010010}. Changing the last 5 bits to 0 gives
\texttt{01000000}, or 64. The network address is \texttt{167.199.170.64/27}.

subnet has 16 addresses. Four subnets need two more 1s on the site prefix, so the subnet

\subsection*{Example: first and last address of a block}

One address of a block is \texttt{205.16.37.39/28}. In binary it is
\texttt{11001101 00010000 00100101 00100111}.

Setting the $32 - 28 = 4$ rightmost bits to 0 gives
\texttt{11001101 00010000 00100101 00100000}, which is \texttt{205.16.37.32}. Setting the same
4 bits to 1 gives \texttt{11001101 00010000 00100101 00101111}, which is
\texttt{205.16.37.47}.

The same result comes from the mask, which for \texttt{/28} is
\texttt{11111111 11111111 11111111 11110000}. ANDing the address with the mask gives the first
address. ORing it with the complement of the mask gives the last address. Complementing the
mask, reading it as a decimal number and adding 1 gives the number of addresses.

Write each octet in 8-bit binary.

third octet must be calculated.

\texttt{Block Size = 256 $-$ 192 = 64} \\

\midrule
0 & 0--63 \\
64 & 64--127 ($\leftarrow$ 84 falls here) \\
128 & 128--191 \\
192 & 192--255 \\
\bottomrule
\end{tabularx}

So the subnet starts at \textbf{64}.

\begin{tabularx}{\textwidth}{@{}X@{}}
\texttt{First two octets unchanged: 19.30} \\
\texttt{Third octet: 64} \\
\texttt{Fourth octet: always 0} \\

\textbf{Subnetwork address} & \textbf{\texttt{19.30.64.0}} \\
\bottomrule
\end{tabularx}

\subsection*{Question 5}

A router receives a packet with destination address \texttt{190.240.33.91}. Show how the

\subsubsection*{Given}

\texttt{Destination Address = 190.240.33.91} \\
\texttt{Prefix (subnet) = /19} \\
\end{tabularx}

Two different things are asked, using two different masks: the \textbf{network

\textbf{subnetwork address} uses the given \texttt{/19} mask.

\subsubsection*{Part A: Network Address (Classful)}

\textbf{Step A1: Identify the class.} The first octet is 190. Since
$128 \le 190 \le 191$, this is a \textbf{class B} address.

\textbf{Step A2: Default mask.} The class B default mask is
\texttt{255.255.0.0} (\texttt{/16}): the first two octets are network, the last
two are host.

\textbf{Step A3: Apply the AND.}

\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\rowcolor{tablehead}\textbf{Line} & \textbf{Binary} \\
\midrule
IP (\texttt{190.240.33.91}) & \texttt{10111110 11110000 00100001 01011011} \\

\bottomrule
\end{tabularx}

So the \textbf{network address is \texttt{190.240.0.0}}.

\subsubsection*{Part B: Subnetwork Address (/19)}

\textbf{Step B1: Convert the mask.} \texttt{/19} is

\textbf{Step B2: Block size in the third octet.}
\texttt{Block Size = 256 $-$ 224 = 32}.

\textbf{Step B3: Locate the block.} The third octet of the IP is \textbf{33}.
Multiples of 32 give the blocks 0--31, 32--63, and so on; 33 falls in

\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\rowcolor{tablehead}\textbf{Term} & \textbf{Value} \\

wasted space. Sorting descending gives $120 \to 60 \to 10$, exactly as in

order differs.

\subsection*{Question 21}

A company needs approximately 600 addresses. For each of the following sets of class C
blocks, determine whether a valid supernet can be formed and explain why.

\subsubsection*{Given}

\begin{tabularx}{\textwidth}{@{}X@{}}
\texttt{Requirement: about 600 addresses} \\
\texttt{Four candidate sets of /24 blocks (see below)} \\
\end{tabularx}

\subsubsection*{Rules for a Valid Supernet}

A set of class C (\texttt{/24}) blocks can be combined into one valid supernet
only if \textbf{all three} conditions hold: (1) the \textbf{number of blocks}
is a power of 2 (1, 2, 4, 8, 16, \ldots), so a single contiguous mask can
represent them; (2) the blocks are \textbf{contiguous} (consecutive network
numbers with no gaps); (3) the \textbf{first block number is an exact multiple
of the block count} (correct address alignment and boundary).

\subsubsection*{(a) 198.47.32.0, 198.47.33.0, 198.47.34.0}

\begin{tabularx}{\textwidth}{@{}X@{}}
\texttt{Number of blocks = 3} \\
\end{tabularx}

Three is not a power of 2 ($2^{1} = 2$, $2^{2} = 4$, with no exact match for 3).
\textbf{Result: invalid.} A single supernet mask cannot represent exactly 3
class C networks; either 2 or 4 blocks would be needed.

\subsubsection*{(b) 198.47.32.0, 198.47.42.0, 198.47.52.0, 198.47.62.0}

\begin{tabularx}{\textwidth}{@{}X@{}}
\texttt{Number of blocks = 4 = $2^{2}$ (power of 2)} \\
\end{tabularx}

Check contiguity: 32, 42, 52, 62 differ by 10 each, not by 1.
\textbf{Result: invalid.} The blocks are not contiguous (ranges 33--41, 43--51
and 53--61 are missing), so they cannot be aggregated under one supernet mask.

\subsubsection*{(c) 198.47.31.0, 198.47.32.0, 198.47.33.0, 198.47.52.0}

\begin{tabularx}{\textwidth}{@{}X@{}}
\texttt{Number of blocks = 4 = $2^{2}$ (power of 2)} \\
\end{tabularx}

Check contiguity: 31, 32, 33 are consecutive, but then the set jumps to 52, a
large gap. \textbf{Result: invalid.} The fourth block is not contiguous with
the first three, so no single supernet range can cover all four.

\subsubsection*{(d) 198.47.32.0, 198.47.33.0, 198.47.34.0, 198.47.35.0}

\begin{tabularx}{\textwidth}{@{}X@{}}
\texttt{Number of blocks = 4 = $2^{2}$ (power of 2)} \\
\texttt{Contiguity: 32, 33, 34, 35 are consecutive} \\
\texttt{Alignment: for 4 blocks the start must be a multiple of 4; 32 $\div$ 4 = 8 exactly} \\
\end{tabularx}

\textbf{Result: valid.} The combined range is
\texttt{198.47.32.0}--\texttt{198.47.35.255}, giving $4 \times 256 = 1024$
addresses under the mask \texttt{/22} (\texttt{255.255.252.0}), which covers the
required 600 addresses.

\subsubsection*{Final Answer}

\begin{tabularx}{\textwidth}{@{}lcccX@{}}
\toprule
\rowcolor{tablehead}\textbf{Set} & \textbf{Blocks} & \textbf{Power of 2?} & \textbf{Contiguous?} & \textbf{Result} \\
\midrule
(a) \texttt{198.47.32/33/34.0} & 3 & No & Yes & \textbf{Invalid} -- 3 is not a power of 2 \\
(b) \texttt{198.47.32/42/52/62.0} & 4 & Yes & No & \textbf{Invalid} -- gaps of 10 between blocks \\
(c) \texttt{198.47.31/32/33/52.0} & 4 & Yes & No & \textbf{Invalid} -- block 52 breaks contiguity \\
(d) \texttt{198.47.32/33/34/35.0} & 4 & Yes & Yes & \textbf{Valid} -- aligned, \texttt{198.47.32.0}--\texttt{198.47.35.255} \\
\bottomrule
\end{tabularx}

\unitpart{Cloud Computing Fundamentals}

\section{Importance of Cloud Computing}

\field{Short description:}{Cloud computing lets an organisation obtain computing resources as
a service instead of buying and running them itself.}

\field{Motivating example:}{Suppose tomorrow you want to start an online shopping website.
What things do you need?}

\begin{itemize}\itemsep2pt
  \item Computer / server
  \item Storage
  \item Internet
  \item Database
  \item Operating system
  \item Software
  \item Security
  \item Application
\end{itemize}

\field{The point:}{Every one of these can be rented from a cloud provider instead of bought
and maintained, which is why cloud computing matters to a business getting started quickly.}

\section{Cloud Service Models}

\field{Short description:}{A cloud service model defines how much of the computing stack the
provider manages on the consumer's behalf.}

\subsection{Overview}

\begin{itemize}\itemsep2pt
  \item \textbf{IaaS} -- Infrastructure as a Service
  \item \textbf{PaaS} -- Platform as a Service
  \item \textbf{SaaS} -- Software as a Service
\end{itemize}

\section{Infrastructure as a Service (IaaS)}

\field{Short description:}{IaaS gives the provider's access to fundamental resources such as
physical machines, virtual machines and virtual storage.}

\field{Also offered:}{}

\begin{itemize}\itemsep2pt
  \item Virtual machine disk storage
  \item Virtual local area networks (VLANs)
  \item Load balancers
  \item IP addresses
  \item Software bundles
\end{itemize}

\field{How it works:}{All of the above resources are made available to the end user via server
virtualization, and are accessed by the customer as if they own them.}

\subsection{Architecture diagram}
\mmd{24-iaas-architecture.png}

\subsection{Benefits}

IaaS allows the cloud provider to freely locate the infrastructure over the Internet in a
cost-effective manner. Key benefits:

\begin{itemize}\itemsep2pt
  \item Full control of the computing resources through administrative access to VMs.
  \item Flexible and efficient renting of computer hardware.
  \item Portability and interoperability with legacy applications.
\end{itemize}

\subsection{Issues}

IaaS shares issues with PaaS and SaaS, such as network dependence and browser-based risks. It
also has issues specific to itself:

\field{Compatibility with legacy security vulnerabilities:}{Because IaaS lets the consumer run
legacy software on the provider's infrastructure, it exposes the consumer to all of the
security vulnerabilities of that legacy software.}

\field{Virtual machine sprawl:}{A VM can fall out of date with respect to security updates
because IaaS allows the consumer to run, suspend or power off virtual machines at will. The
provider can automatically update such VMs, but the mechanism is hard and complex.}

\field{Robustness of VM-level isolation:}{IaaS offers each consumer an isolated environment
through the hypervisor, a software layer with hardware support for virtualization that splits
one physical computer into multiple virtual machines.}

\field{Data erase practices:}{Consumers use virtual machines that share the provider's common
disk resources. When a consumer releases a resource, the provider must ensure the next
consumer to rent it does not see data residue from the previous one.}

\subsection{Characteristics}

\begin{itemize}\itemsep2pt
  \item Virtual machines with pre-installed software.
  \item Virtual machines with pre-installed operating systems, such as Windows or Linux.
  \item On-demand availability of resources.
  \item Ability to store copies of the same data in different locations.
  \item Computing resources that can be easily scaled up and down.
\end{itemize}

\section{Platform as a Service (PaaS)}

\field{Short description:}{PaaS offers the development and deployment tools required to build
applications, including point-and-click tools that let non-developers create web
applications. Google App Engine and Force.com are example PaaS vendors -- a developer logs
into these platforms and uses their built-in API to build web applications.}

\field{Main drawback:}{Developer lock-in with a particular vendor. An application written in
Python against Google's App Engine API is likely to work only in that environment, so vendor
lock-in is the biggest problem in PaaS.}

\subsection{Architecture diagram}
\mmd{25-paas-architecture.png}

\subsection{Benefits}

\field{Lower administrative overhead:}{The cloud provider is responsible for administration,
so the consumer need not worry about it.}

\field{Lower total cost of ownership:}{The consumer need not purchase expensive hardware,
servers, power or data storage.}

\field{Scalable solutions:}{Very easy to scale up or down automatically based on application
resource demand.}

\field{More current system software:}{The provider is responsible for maintaining software
versions and patch installations.}

\subsection{Issues}

\field{Lack of portability between PaaS clouds:}{Although standard languages are used, the
implementation of platform services may vary. File, queue or hash-table interfaces of one
platform may differ from another's, making it hard to move workloads between platforms.}

\field{Event based processor scheduling:}{PaaS applications are event oriented, which places
resource constraints on them -- they must answer a request within a given interval of time.}

\field{Security engineering of PaaS applications:}{Because PaaS applications depend on the
network, they must explicitly use cryptography and manage security exposures.}

\subsection{Characteristics}

\begin{itemize}\itemsep2pt
  \item Browser-based development environment; developers create databases and edit
        application code via an API or point-and-click tools.
  \item Built-in security, scalability and web service interfaces.
  \item Built-in tools for defining workflow, approval processes and business rules.
  \item Easy to integrate with other applications on the same platform.
  \item Web service interfaces that connect applications outside the platform.
\end{itemize}

\section{Software as a Service (SaaS)}

\field{Short description:}{SaaS provides a software application as a service to end users --
software deployed on a hosted service and accessed via the Internet.}

\field{Example SaaS applications:}{}

\begin{itemize}\itemsep2pt
  \item Billing and invoicing systems
  \item Customer Relationship Management (CRM) applications
  \item Help desk applications
  \item Human Resource (HR) solutions
\end{itemize}

\field{Customisation:}{Some SaaS applications are not customisable, such as an office suite.
But SaaS also provides an API that lets a developer build a customised application on top.}

\subsection{Characteristics}

\begin{itemize}\itemsep2pt
  \item Software is made available over the Internet.
  \item The software is maintained by the vendor, not by where it runs.
  \item Licensing may be subscription based or usage based, and is billed on a recurring
        basis.
  \item Cost effective, since there is no maintenance burden on the end user.
  \item Available on demand, and can be scaled up or down on demand.
  \item Automatically upgraded and updated.
  \item Offers a shared data model, so multiple users share a single instance of the
        infrastructure without hard-coding functionality per user.
  \item All users run the same version of the software.
\end{itemize}

\subsection{Benefits}

\begin{itemize}\itemsep2pt
  \item Modest software tools
  \item Efficient use of software licenses
  \item Centralised management and data
  \item Platform responsibilities managed by the provider
  \item Multitenant solutions
\end{itemize}

\subsection{Issues}

\field{Browser based risks:}{If the consumer visits a malicious website and the browser is
infected, subsequent access to a SaaS application can compromise the consumer's data. Using
multiple browsers, dedicating one to SaaS access, or using a virtual desktop reduces the
risk.}

\field{Network dependence:}{A SaaS application can only be delivered while the network is
continuously available, and network reliability cannot be guaranteed by either the provider
or the consumer.}

\field{Lack of portability between SaaS clouds:}{Transferring workloads from one SaaS cloud to
another is not easy, because workflow, business logic, user interfaces and support scripts
can all be provider specific.}

\subsection{Public Cloud}

\field{Short description:}{The public cloud allows systems and services to be easily
accessible to the general public -- for example, Google, Amazon and Microsoft offer cloud
services over the Internet.}

\field{Benefits:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Cost effective} -- shares the same resources across a large number of
        consumers, so it has low cost.
  \item \textbf{Reliability} -- draws on large numbers of resources from different locations,
        so a failed resource can be replaced by another one.
  \item \textbf{Flexibility} -- easy to integrate with a private cloud, giving consumers a
        flexible approach.
  \item \textbf{Location independence} -- services are delivered through the Internet.
  \item \textbf{Utility style costing} -- pay-per-use, with resources accessible whenever the
        consumer needs them.
  \item \textbf{High scalability} -- resources are made available on demand from a pool, and
        can be scaled up or down as required.
\end{itemize}

\field{Disadvantages:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Low security} -- data is hosted off-site on publicly shared resources, so it
        does not ensure a high level of security.
  \item \textbf{Less customisable} -- comparatively less customisable than a private cloud.
\end{itemize}

\subsection{Private Cloud}

\field{Short description:}{The private cloud allows systems and services to be accessible
within a single organisation, which may manage it internally or through a third party.}

\field{Benefits:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Higher security and privacy} -- not available to the general public, and
        resources are shared from a distinct pool, ensuring higher security and privacy.
  \item \textbf{More control} -- more control over resources and hardware than a public cloud,
        because it is accessed only within the organisation.
  \item \textbf{Cost and energy efficiency} -- not as cost effective as public clouds, but
        offers more efficiency than a public cloud.
\end{itemize}

\field{Disadvantages:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Restricted area} -- accessible only locally, and difficult to deploy globally.
  \item \textbf{Inflexible pricing} -- purchasing new hardware to meet demand is very costly.
  \item \textbf{Limited scalability} -- can be scaled only within the capacity of the
        internally hosted resources.
\end{itemize}

\subsection{Hybrid Cloud}

\field{Short description:}{The hybrid cloud is a mixture of public and private cloud.
Non-critical activities are performed using the public cloud, while critical activities are
performed using the private cloud.}

\field{Benefits:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Scalability} -- offers both public cloud scalability and private cloud
        scalability.
  \item \textbf{Flexibility} -- offers both secure resources and scalable public resources.
  \item \textbf{Cost efficiencies} -- public cloud is more cost effective than private, so the
        hybrid cloud gains this saving.
  \item \textbf{Security} -- the private cloud portion ensures a higher degree of security.
\end{itemize}

\field{Disadvantages:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Networking issues} -- networking becomes complex due to the presence of both
        private and public cloud.
  \item \textbf{Security compliance} -- it is necessary to ensure cloud services comply with
        the organisation's security policies.
\end{itemize}

\subsection{Community Cloud}

\field{Short description:}{The community cloud allows systems and services to be accessible by
a group of organisations, sharing infrastructure among several organisations from a specific
community. It may be managed internally or by a third party.}

\field{Benefits:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Cost effective} -- offers the same advantage as a private cloud at lower cost.
  \item \textbf{Sharing between organisations} -- provides infrastructure to share cloud
        resources and capabilities among several organisations.
  \item \textbf{Security} -- comparatively more secure than the public cloud.
\end{itemize}

\field{Issues:}{Since all data is housed at one location, care is needed in storing data in a
community cloud, because it might be accessible by others. Allocating responsibility for
governance, security and cost is also challenging.}

\section{Regions, Availability Zones and Edge Locations}

\field{Short description:}{Cloud providers such as AWS, Microsoft Azure and Google Cloud have
data centres distributed across the world. To organise this global infrastructure and provide
reliable, fast and highly available services, they use the concepts of Regions, Availability
Zones and Edge Locations.}

\subsection{Region}

\field{Definition:}{A Region is a geographical area of the world in which a cloud provider
operates one or more data centres or Availability Zones. Providers divide their global
infrastructure into regions so customers can choose where their cloud resources are
deployed.}

\field{Example AWS regions:}{Mumbai, Singapore, Tokyo, London, Frankfurt, Northern Virginia,
Sydney. Azure and Google Cloud have their own geographical regions.}

\field{Why regions are required:}{If a company operates in India with customers primarily
located in India, but hosts its application in a distant location such as the United States,
communication may take longer because data has to travel a greater distance. Deploying the
application in an Indian region instead helps reduce network latency.}

\field{Characteristics:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Geographical location} -- a region represents a specific geographical area.
  \item \textbf{Contains multiple Availability Zones} -- a region is generally divided into
        multiple isolated Availability Zones.
  \item \textbf{Data residency} -- organisations can choose a region based on where they want
        their data and applications hosted, subject to the provider's services and applicable
        regulations.
  \item \textbf{Disaster recovery} -- organisations can use multiple regions for disaster
        recovery.
  \item \textbf{Reduced latency} -- selecting a region closer to users reduces network
        latency.
  \item \textbf{Service availability} -- not every cloud service is necessarily available in
        every region.
\end{itemize}

\subsection{Availability Zone}

\field{Definition:}{An Availability Zone (AZ) is an isolated infrastructure location within a
cloud Region. A Region contains multiple AZs, designed to operate independently enough that a
failure in one AZ does not necessarily affect the others.}

\field{Why AZs are required:}{The main purpose of Availability Zones is high availability and
fault tolerance. If a company runs its entire application in only one Availability Zone, and
that AZ experiences a power failure, network failure, hardware failure, cooling failure or
other infrastructure problem, the application may become unavailable. Distributing resources
across multiple AZs avoids this.}

\field{Characteristics:}{}

\begin{itemize}\itemsep2pt
  \item \textbf{Isolation} -- AZs are designed to be isolated from failures in other AZs.
  \item \textbf{Independent infrastructure} -- each AZ has independent power, cooling,
        networking and physical facilities, reducing the chance a single failure affects all
        AZs.
  \item \textbf{High availability} -- applications can be deployed across multiple AZs.
  \item \textbf{Fault tolerance} -- using multiple AZs lets applications tolerate certain
        infrastructure failures.
  \item \textbf{Low-latency communication} -- AZs within a region are connected by the
        provider's high-speed network, so applications distributed across AZs communicate
        efficiently.
\end{itemize}

\subsection{Edge Location}

\field{Definition:}{An Edge Location is a distributed location where a cloud provider's
services can cache or deliver content closer to end users. Edge locations are particularly
important for Content Delivery Networks (CDNs) -- for example, AWS uses Amazon CloudFront to
deliver content through a global network of edge locations.}

\field{Why edge locations are required:}{Consider a user in Nagpur accessing a website whose
main server is in the United States. Without caching, the request must travel that long
distance, resulting in higher latency. With an edge location, the user instead receives
cached content from a location closer to them, giving faster delivery and lower latency.}

\field{How they work:}{A website's images, videos, CSS files, JavaScript files, web pages and
other static content are cached across edge locations. When a user requests this content, the
CDN serves it from the nearest appropriate edge location.}

\subsection{Relationship between Region, AZ and Edge Location}
\mmd[0.36]{27-region-az-edge.png}

\begin{itemize}\itemsep2pt
  \item A \textbf{Region} is where cloud resources are deployed.
  \item An \textbf{Availability Zone} provides isolation and redundancy within a Region.
  \item An \textbf{Edge Location} brings frequently accessed content and services closer to
        users.
  \item If one AZ fails, traffic is served by the other AZs, which ensures high availability
        and fault tolerance.
\end{itemize}

national borders. Data centres may be located far from the data owner's country, and laws may

adoption and compliance.}

\field{Application security:}{Application developers are responsible for security beyond

\section{Fundamentals of Pricing: Total Cost of Ownership}

\field{Simple idea:}{}

\[

\text{Other associated costs}

\section{Amazon S3: Simple Storage Service}

\field{Short description:}{Amazon S3 is a fully managed \textbf{object storage} service that
stores data as objects inside buckets, and is accessed over the web.}

\subsection{Overview}

\field{Object storage:}{S3 is object storage, not traditional file or block storage. It
provides a file-system-like structure, but data is actually stored and managed as objects.}

\field{Introduced in 2006:}{S3 was one of the earliest services launched by AWS.}

\field{Fully managed:}{AWS handles the underlying storage infrastructure, maintenance and
scalability.}

\field{Highly durable and scalable:}{Designed for high durability, security and scalability,
protecting data against the loss of multiple facilities through redundant storage.}

\field{Pay-as-you-go pricing:}{No upfront infrastructure costs or minimum commitments; you pay
based on actual usage, such as storage and data transfer.}

\field{Integration with AWS services:}{Integrates easily with EC2 for computing, CloudFront for
content delivery and RDS for database applications.}

\subsection{Access methods}

\bottomrule
\end{tabularx}

\subsection{Fundamental constructs}

\field{Buckets and objects:}{S3 stores data as \textbf{objects} within \textbf{buckets}. An
object consists of a file and, optionally, any metadata that describes that file.}

\mmd[0.45]{30-s3-bucket-object.png}

\subsubsection{Buckets}

\begin{itemize}\itemsep2pt
  \item \textbf{Containers for objects} -- a bucket stores and organises objects.
  \item \textbf{Namespace organisation} -- buckets provide a unique namespace for objects.
  \item \textbf{Globally unique names} -- each bucket name must be unique across all of S3.
  \item \textbf{Naming length} -- a bucket name must contain 3 to 63 characters.
  \item \textbf{DNS-compatible naming} -- bucket names must follow DNS naming conventions.
  \item \textbf{Bucket limit} -- an account has a default service limit on the number of
        buckets, which can be increased when required.
\end{itemize}

\subsubsection{Objects}

\begin{itemize}\itemsep2pt
  \item \textbf{Data and metadata} -- an object is the actual data (file) plus metadata that
        describes it.
  \item \textbf{Unique identification} -- each object is identified by its \textbf{key}
        (name) and, when versioning is enabled, a \textbf{version ID}.
  \item \textbf{Number of objects} -- no fixed limit on objects per bucket.
  \item \textbf{Object size} -- an individual object can be larger than 5 TB.
  \item \textbf{Different storage classes} -- objects in the same bucket can belong to
        different storage classes.
  \item \textbf{Storage Inventory} -- produces a flat-file listing of objects and their
        metadata, in formats such as CSV or JSON.
\end{itemize}

\subsubsection{Keys}

\begin{itemize}\itemsep2pt
  \item \textbf{Unique identifier} -- the object key identifies an object within a bucket.
  \item \textbf{Maximum length} -- up to 1,024 bytes, including any path prefix such as
        \texttt{images/2026/}.
\end{itemize}

\field{Structure of an S3 URL:}{\texttt{https://\textit{bucket-name}.s3.amazonaws.com/%
\textit{key}}, for example \texttt{https://college-notes-2026.s3.amazonaws.com/images/logo.png}.}

\subsection{Storage classes}

\subsubsection{S3 Standard}

\begin{itemize}\itemsep2pt
  \item \textbf{Frequently accessed (``hot'') data} -- dynamic websites, content distribution,
        mobile and gaming applications, big-data analytics.
  \item \textbf{Low latency and high throughput.}
  \item \textbf{Durability} -- 99.999999999\% (11 nines); expected annual loss of about
        0.000000001\% of objects.
  \item \textbf{Availability} -- 99.99\%.
  \item \textbf{No minimum storage duration.}
\end{itemize}

\subsubsection{S3 Standard-IA (Infrequent Access)}

\begin{itemize}\itemsep2pt
  \item \textbf{Infrequently accessed data that still needs high performance} -- long-term
        storage, backups, disaster-recovery data.
  \item \textbf{Low latency and high throughput} when the data is needed.
  \item \textbf{Durability} -- 11 nines. \textbf{Availability} -- 99.9\%.
  \item \textbf{Lower storage cost} than Standard, but a \textbf{retrieval fee} is charged.
  \item \textbf{Minimum storage duration} -- 30 days.
\end{itemize}

\subsubsection{S3 RRS (Reduced Redundancy Storage)}

\begin{itemize}\itemsep2pt
  \item \textbf{Non-critical, reproducible data} already stored safely elsewhere.
  \item \textbf{Protection against facility loss} -- withstands the loss of data in a single
        facility.
  \item \textbf{Durability} -- 99.99\% (about 0.01\% expected annual loss).
        \textbf{Availability} -- 99.99\%.
\end{itemize}

\subsubsection{Amazon Glacier}

\begin{itemize}\itemsep2pt
  \item \textbf{Cold storage} -- long-term archiving of rarely accessed data.
  \item \textbf{Archives and vaults} -- data is stored as archives, organised in vaults.
  \item \textbf{Durability} -- 11 nines. \textbf{Availability} -- 99.99\%.
  \item \textbf{Retrieval options} -- Expedited (about 1--5 minutes), Standard (about 3--5
        hours), Bulk (about 5--12 hours).
  \item \textbf{Vault Lock} -- stores data as immutable objects for compliance, preventing
        unauthorised change or deletion.
  \item \textbf{Minimum storage duration} -- 90 days.
\end{itemize}

\section{Amazon EBS: Elastic Block Store}

\begin{sh}
sudo mount -t nfs4 fs-12345678.efs.ap-south-1.amazonaws.com:/ /mnt/efs

\field{Mount target:}{To reach the file system from instances in a VPC, you create
\textbf{mount targets} in the VPC. A mount target is an NFS v4 endpoint with an IP address
and a DNS name, used in the mount command -- one per Availability Zone.}

  \item \textbf{File permissions} -- user-level read-write-execute permissions for users and

  \item \textbf{IAM integration} -- IAM policies control who may use the administrative APIs

\end{itemize}

  \item All reads and writes are \textbf{fully consistent across AZs}: a read in one AZ is

\section{Content Delivery Networks (CDN)}

\field{Short description:}{A CDN is a network of servers placed at the edge of the Internet
that keeps copies of content close to end users, so pages and media load faster and the
origin server carries less load.}

\subsection{Why a CDN is needed}

\field{Simple on the outside:}{From outside, the web looks simple: content providers on one
side, end users on the other, with ``the Internet'' between them.}

\field{Problematic on the inside:}{In reality a request crosses many network providers (UUNet,
Qwest, AOL and others) joined at peering points (NAPs). Each hop adds delay and risk.}

\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\rowcolor{tablehead}\textbf{Issue} & \textbf{What the user sees} \\
\midrule
Latency & The browser takes a long time to load pages. \\
Packet loss & The browser hangs; the user needs to hit refresh. \\
Jitter & Streams are jerky. \\
Server load & The browser connects but does not fully load the page. \\
Bandwidth aggregation & Many users share congested links. \\
Broken or missing content & Parts of the page fail to appear. \\
\bottomrule
\end{tabularx}

\field{The solution:}{Place servers at the network edge, close to end users, and serve
content from them.}

\mmd[0.39]{38-cdn-conventional-vs-cdn.png}

\subsection{Passive and active CDNs}

\begin{tabularx}{\textwidth}{@{}XX@{}}
\toprule

\midrule

  customisation. \\
The provider lacks control and customisation. & Low investment from the content provider. \\
\bottomrule
\end{tabularx}

\end{itemize}

\subsection{Directing clients to a replica}

\field{HTTP redirects (application based):}{The origin server rewrites its pages so that

\section{Amazon CloudFront}

\field{Short description:}{Amazon CloudFront is AWS's web service for content delivery. It

\subsection{How CloudFront gives higher performance}

\begin{itemize}\itemsep2pt
  \item A network of \textbf{edge locations} caches copies of popular files close to viewers.
  \item Each request is served by the \textbf{closest edge location}, so it travels a shorter
        distance.
  \item For files not cached at the edge, CloudFront keeps \textbf{persistent connections}
        with the origin, so they are fetched as quickly as possible.
  \item Further optimisations, such as a wider TCP initial congestion window.
  \item \textbf{Request collapsing} -- simultaneous viewer requests for the same file at an
        edge are merged into one origin request, reducing origin load and cost.
\end{itemize}

\subsection{Speeding up an entire website}

\begin{itemize}\itemsep2pt
  \item CloudFront uses the standard \textbf{cache-control headers} you set on your files to
        tell static content from dynamic content.
  \item With AWS origins you also gain route tracking, health monitoring and fast response to
        issues.
  \item Different origins can serve different content on one site -- S3 for static objects,
        EC2 for dynamic content, custom origins for third-party content -- paying only for
        what you use.
\end{itemize}

\subsection{How long files stay at the edge}

\begin{itemize}\itemsep2pt
  \item With no cache-control header, an edge location re-checks the origin for a newer
        version when it gets a request more than \textbf{24 hours} after its last check.
        This is the \textbf{expiration period}.
  \item The expiration period can be set anywhere from 0 seconds upward with cache-control
        headers on the origin's files.
  \item At 0 seconds, CloudFront revalidates every request with the origin.
  \item For files that rarely change, set a long expiration period and use a
        \textbf{versioning} scheme in file names to roll out updates.
\end{itemize}

\section{AWS Snowball and Snowmobile}

\subsection{The problem: moving large data sets}

Cloud computing lets organisations store and process data in S3, EC2 and analytics services,
but moving a large amount of existing data into the cloud can be difficult. Consider a
university with \textbf{500 TB} of research data -- medical images, videos, student project
datasets and simulation results. Uploading it over a normal Internet connection may take
weeks or months. The main challenges:

\begin{itemize}\itemsep2pt
  \item \textbf{Limited bandwidth} -- the connection may not support high-speed uploads.
  \item \textbf{Long transfer time} -- large datasets take substantial time to upload.
  \item \textbf{Network costs} -- data transfer and dedicated connectivity can be expensive.
  \item \textbf{Reliability} -- network interruptions can delay the migration.
  \item \textbf{Security} -- sensitive data must be protected during transfer.
\end{itemize}

\subsection{AWS Snowball and Snowball Edge}

\field{Snowball:}{A secure, ruggedised physical device used to transfer large amounts of data
between an organisation's site and AWS, and for supported edge-computing workloads. Suitable
for terabytes to hundreds of terabytes, depending on device capacity and configuration.}

\field{Snowball Edge:}{A physical device with both \textbf{storage and computing}
capabilities. It moves data to or from AWS without depending entirely on an Internet
connection. The device is connected to the local network, data is copied onto it, and it is
shipped to AWS, which imports the data into the specified S3 destination.}

\subsection{How Snowball works}
\mmd[0.37]{42-snowball-workflow.png}

\begin{enumerate}\itemsep2pt
  \item \textbf{Create a migration job} -- define data volume, destination, device
        configuration and job type in the AWS Snow Family management interface.
  \item \textbf{Receive the device} -- AWS prepares and ships the configured device.
  \item \textbf{Connect the device} -- the IT team connects it to the local network and
        authenticates with the job's security credentials.
  \item \textbf{Copy the data} -- through a supported interface such as NFS or the S3
        adapter.
  \item \textbf{Return the device} -- ship it back to AWS.
  \item \textbf{Import into AWS} -- AWS imports the data into the specified S3 bucket.
  \item \textbf{Verify the migration} -- check the job completion report and success/failure
        logs before removing the original copies.
\end{enumerate}

\subsection*{Problem: upload time for 400 TB}

\subsubsection*{Solution}

\end{tabularx}

\section{Amazon Route 53: DNS Service}

\field{Short description:}{Route 53 is AWS's Domain Name System (DNS) service. It translates
domain names into IP addresses and decides, through routing policies, which resource answers
each request.}

\subsection{DNS background}

\field{IPv4 versus IPv6:}{IPv4 is a 32-bit field with over 4 billion addresses
($256^4 = 4{,}294{,}967{,}296$, from \texttt{0.0.0.0} to \texttt{255.255.255.255}, divided
into classes A, B and C). IPv6 was created to solve the depletion of this space and uses
128-bit addresses.}

\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\rowcolor{tablehead}\textbf{Record} & \textbf{Meaning} \\
\midrule
NS record & \textbf{Name Server} record. Used by top-level-domain servers to direct traffic
  to the content DNS server holding the authoritative records. \\
\addlinespace
A record & \textbf{Address} record, the fundamental type. Translates a domain name to an IP
  address, e.g.\ \texttt{www.zekelabs.com} $\rightarrow$ \texttt{123.10.10.80}. \\
\addlinespace
TTL & \textbf{Time To Live}, in seconds: how long a record is cached on the resolving server
  or the user's PC. A lower TTL makes record changes propagate faster. \\
\addlinespace
CNAME record & \textbf{Canonical Name}: resolves one domain name to another, e.g.\
  \texttt{mobile.google.com} $\rightarrow$ \texttt{m.google.com}. \\
\addlinespace
Alias record & Maps a record set to an ELB, a CloudFront distribution or an S3 website
  bucket. Works like a CNAME, but can be used at the \textbf{zone apex} (naked domain such
  as \texttt{example.com}), which a CNAME cannot. \\
\bottomrule
\end{tabularx}

\field{Why alias records save time:}{Route 53 automatically tracks changes in the resource an
alias points to. If an alias for \texttt{zekelabs.com} points to the load balancer
\texttt{elb1-1234.us-east.elb.amazonaws.com} and the balancer's IP address changes, Route 53
reflects the change in its DNS answers without any edit to the hosted zone.}

\section{Remote Desktop Protocol (RDP)}

\field{Short description:}{RDP is a Microsoft network protocol that lets a user remotely
access and control another computer over a network or the Internet -- seeing its desktop,
opening applications and managing files as if sitting in front of it. It is commonly used to
manage virtual machines on Azure and AWS.}

\subsection{How RDP works}

RDP follows a \textbf{client--server} architecture.

\mmd[0.45]{52-rdp-working.png}

\begin{enumerate}\itemsep2pt
  \item The user opens an RDP client on the local computer.
  \item The client connects to the remote computer by IP address or hostname.
  \item The user authenticates with valid credentials.
  \item The remote computer provides a desktop session.
  \item The user sends keyboard and mouse input.
  \item The remote computer executes it and sends display updates back.
\end{enumerate}

\field{RDP in cloud computing:}{Especially useful for Windows VMs: an Azure administrator can
create a Windows VM and connect to it remotely over RDP, without physical access to the
server.}

\begin{tabularx}{\textwidth}{@{}XX@{}}
\toprule
\rowcolor{tablehead}\textbf{Advantages} & \textbf{Limitations} \\
\midrule
Remote access from different locations. & Requires network connectivity. \\
Centralised management of cloud servers. & Performance depends on network speed and
  latency. \\
Use applications and resources hosted elsewhere. & Wrong security settings can expose systems
  to attack. \\
No physical presence needed. & Mainly for Windows graphical access, though clients exist for
  other platforms. \\
Cost-efficient remote administration of cloud VMs. & Some advanced features need extra
  configuration or licensing. \\
\bottomrule
\end{tabularx}

\section{Secure Shell (SSH)}

\field{Short description:}{SSH is a cryptographic network protocol for securely accessing and
managing remote computers over an unsecured network such as the Internet. It is used to run
commands, transfer files, configure servers and manage cloud resources, especially
Linux VMs on AWS, Azure and Google Cloud.}

\subsection{How SSH works}

The SSH \textbf{client} runs on the user's computer; the SSH \textbf{server} runs on the
remote machine.

\mmd[0.45]{53-ssh-working.png}

\begin{enumerate}\itemsep2pt
  \item \textbf{Initiate connection} -- the user runs an SSH client.
  \item \textbf{Establish secure communication} -- client and server negotiate algorithms and
        set up an encrypted connection.
  \item \textbf{Verify server identity} -- the client checks the server's host key to prevent
        impersonation.
  \item \textbf{Authenticate the user} -- with a password or an SSH key pair.
  \item \textbf{Execute commands} on the remote system.
  \item \textbf{Terminate} -- type \texttt{exit} to close the session.
\end{enumerate}

\begin{sh}
ssh -i college-key.pem azureuser@20.193.45.10    # log in with a key pair
scp -i college-key.pem report.pdf azureuser@20.193.45.10:~/   # copy a file
\end{sh}

\section{Load Balancer}

\field{Short description:}{A load balancer distributes incoming network traffic across
multiple servers or VMs to improve performance, availability, scalability and reliability.
If every request went to a single server it would become overloaded; the load balancer
spreads the requests.}

\field{Example:}{During a major sale, thousands of customers browse and order at the same
time on a shopping website. A load balancer spreads their requests across several application
servers so no single server carries all the traffic.}

\mmd[0.28]{54-load-balancer.png}

\subsection{How a request is handled}

\begin{enumerate}\itemsep2pt
  \item A user sends a request to the website or application.
  \item The request reaches the load balancer.
  \item The load balancer checks its routing rules and server health.
  \item It selects a suitable healthy server.
  \item The selected server processes the request.
  \item The response is returned to the user.
\end{enumerate}

\subsection{Objectives}

\begin{itemize}\itemsep2pt
  \item \textbf{Scalability} -- distributes traffic as the number of users grows.
  \item \textbf{High availability} -- keeps routing to healthy servers when one fails.
  \item \textbf{Performance} -- no single server becomes a bottleneck.
  \item \textbf{Fault tolerance} -- reduces the impact of individual server failures.
  \item \textbf{Efficient resource utilisation} -- spreads work across available servers.
  \item \textbf{Maintenance support} -- servers can be taken out of service for maintenance.
\end{itemize}

\subsection{Types of load balancers}

\field{By deployment:}{}

\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\rowcolor{tablehead}\textbf{Type} & \textbf{Description} \\
\midrule
Hardware & A physical appliance in a data centre; common where dedicated network equipment is
  required. \\
Software & An application that distributes traffic, running on VMs or containers, e.g.\
  HAProxy and NGINX. \\
Cloud & A managed cloud service that distributes traffic without the user managing any
  load-balancing hardware. \\
\bottomrule
\end{tabularx}

\field{By network layer:}{}

\begin{tabularx}{\textwidth}{@{}lXX@{}}
\toprule
\rowcolor{tablehead}\textbf{Layer} & \textbf{Decides using} & \textbf{Example and typical
  use} \\
\midrule
Layer 4 (transport) & TCP/UDP connection information: IP addresses and port numbers & Send TCP
  traffic on port 443 to a backend server; high-performance traffic distribution \\
\addlinespace
Layer 7 (application) & HTTP headers, hostnames, URL paths and cookies & Route
  \texttt{/products} to product servers and \texttt{/payments} to payment servers; websites,
  APIs and microservices \\
\bottomrule
\end{tabularx}

\subsection{Load-balancing algorithms}

\begin{tabularx}{\textwidth}{@{}lXX@{}}
\toprule
\rowcolor{tablehead}\textbf{Algorithm} & \textbf{How it works} & \textbf{Advantage} \\
\midrule
Round robin & Requests go to servers in turn: 1 $\rightarrow$ A, 2 $\rightarrow$ B,
  3 $\rightarrow$ C, then repeat & Simple and easy to understand \\
\addlinespace
Least connections & A new request goes to the eligible server with the fewest active
  connections & Good when requests take different times to process \\
\addlinespace

  get more & Handles servers of different capacity \\
\addlinespace

  client, depending on configuration \\
\bottomrule
\end{tabularx}

\subsection{Health checks}

\field{Short description:}{A health check tests whether a backend server is working
correctly.}

\begin{itemize}\itemsep2pt
  \item The load balancer periodically sends a request, for example HTTP \texttt{GET /health}.
  \item If Server A responds successfully, it stays eligible for traffic.
  \item If Server B fails the configured check, it receives no new requests.
  \item When Server B is healthy again, it is returned to service.
  \item Health checks improve availability but do not prove that every function of the
        application works -- the health endpoint must be designed carefully.
\end{itemize}

\section{Auto Scaling}

\field{Short description:}{Auto Scaling automatically increases or decreases the computing
resources allocated to an application according to its workload, keeping performance up while
controlling cost.}

\field{Example:}{A shopping website has 2,000 users on a normal day and 50,000 during a major
sale. Auto Scaling adds VM instances to handle the extra traffic and removes them when demand
falls.}

\mmd[0.30]{57-auto-scaling.png}

\subsection{Why we need it}

Without Auto Scaling, administrators must add or remove resources by hand, risking poor
performance or wasted spending. Its objectives:

\begin{itemize}\itemsep2pt
  \item \textbf{High availability} -- keeps applications running as demand changes.
  \item \textbf{Better performance} -- adds resources when the workload rises.
  \item \textbf{Cost optimisation} -- removes unneeded resources when demand falls.
  \item \textbf{Automatic resource management} -- less manual intervention.
  \item \textbf{Elasticity} -- resources adapt to workload changes.
  \item \textbf{Fault tolerance} -- can replace unhealthy instances.
\end{itemize}

\subsection{Types of scaling}

\midrule

\addlinespace
Vertical & Resources of an existing machine & Upgrade a VM from 2 vCPU / 4 GB to 8 vCPU / 16
  GB \\
\addlinespace
Scheduled & Capacity on a predefined schedule & Add capacity before online examination
  hours \\
\addlinespace
Dynamic & Capacity in response to real-time metrics & Add instances while CPU stays above

\section{Load Balancing and Auto Scaling Numericals}

\subsection*{Problem 1: Can four servers handle the load?}

An e-commerce website receives 12,000 requests per minute. A load balancer distributes them
equally among 4 web servers; each server can handle 3,500 requests per minute. Find the
requests per server, the total capacity, and whether the servers can cope.

\subsubsection*{Solution}

\begin{tabularx}{\textwidth}{@{}lX@{}}
Requests per server & $\dfrac{12{,}000}{4} = 3{,}000$ per minute \\[8pt]
Total capacity & $4 \times 3{,}500 = 14{,}000$ per minute \\
Can they cope? & Yes: capacity 14,000 $>$ traffic 12,000 \\
Unused capacity & $14{,}000 - 12{,}000 = \textbf{2,000 requests/minute}$ \\
\end{tabularx}

\subsection*{Problem 2: Instances needed at peak}

An application runs on 3 VM instances, each handling 2,000 requests per minute. At peak,
traffic rises to 15,000 requests per minute and Auto Scaling adds instances as required. Find
the initial capacity, the minimum instances for peak traffic, and the instances Auto Scaling
must add.

\subsubsection*{Solution}

\begin{tabularx}{\textwidth}{@{}lX@{}}
Initial capacity & $3 \times 2{,}000 = 6{,}000$ per minute \\
Minimum instances & $\dfrac{15{,}000}{2{,}000} = 7.5$, rounded \textbf{up} to \textbf{8}
  instances (instances are whole numbers) \\[8pt]
Additional instances & $8 - 3 = \textbf{5 instances}$ \\
\end{tabularx}

\subsection*{Problem 3: Load balancer plus Auto Scaling}

An application receives 24,000 requests per minute. Initially 4 servers are available, each
handling 4,000 requests per minute. The load balancer distributes requests equally, and Auto
Scaling adds servers of the same capacity when needed. Find the requests per server before
scaling, the initial capacity, the minimum total servers, and the additional servers.

\subsubsection*{Solution}

\begin{tabularx}{\textwidth}{@{}lX@{}}
Requests per server before scaling & $\dfrac{24{,}000}{4} = 6{,}000$ per minute (over the
  4,000 limit) \\[8pt]
Initial capacity & $4 \times 4{,}000 = 16{,}000$ per minute \\
Minimum total servers & $\dfrac{24{,}000}{4{,}000} = \textbf{6}$ \\[8pt]
Additional servers & $6 - 4 = \textbf{2 servers}$ \\
\end{tabularx}
