\section{Git}

Git tracks every change, lets a team work on the same code without collisions, and
lets you undo a mistake. These commands cover the everyday work and the recovery
tools you reach for when something has gone wrong.

\subsection{Installation}

\begin{sh}
# Windows
winget install Git.Git
winget install GitHub.cli
# macOS
brew install git gh
# Linux (Debian/Ubuntu) -- git is in the base repositories, gh is not
sudo apt install git
\end{sh}

The GitHub CLI needs its own apt repository on Debian and Ubuntu:

\begin{sh}
sudo mkdir -p -m 755 /etc/apt/keyrings
wget -qO- https://cli.github.com/packages/githubcli-archive-keyring.gpg | \
  sudo tee /etc/apt/keyrings/githubcli-archive-keyring.gpg > /dev/null
sudo chmod go+r /etc/apt/keyrings/githubcli-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) \
  signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] \
  https://cli.github.com/packages stable main" | \
  sudo tee /etc/apt/sources.list.d/github-cli.list > /dev/null
sudo apt update && sudo apt install gh
\end{sh}

\field{First run:}{\texttt{git} refuses to commit until it knows who you are, and
\texttt{gh} needs a token before it can reach GitHub. Do both once per machine:}

\begin{sh}
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
gh auth login
\end{sh}

\field{Verify:}{\texttt{git -{}-version} and \texttt{gh -{}-version}.
\texttt{gh auth status} says whether the token is still good.}

\section{Docker}

Docker packages an application and everything it needs into a portable container, so
it runs the same way on a laptop, in CI and in production.

\subsection{Installation}

\begin{sh}
# Windows
winget install Docker.DockerDesktop
# macOS -- drop --cask for the CLI alone, against a remote or Colima daemon
brew install --cask docker
# Linux
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
\end{sh}

\field{On Linux, the \texttt{usermod} line matters.}{It is what lets you run
\texttt{docker} without \texttt{sudo}, and it only takes effect after you log
out and back in. On Windows and macOS, Docker Desktop has to be launched once
before the CLI can talk to anything.}

\field{Verify:}{\texttt{docker -{}-version} prints the Engine version.
\texttt{Cannot connect to the Docker daemon} means Docker is installed but not
running, which is a different problem.}

\section{Kubernetes}

Kubernetes is the conductor of a container orchestra. It automates the deployment,
scaling and management of containerised applications across a cluster of machines.

\subsection{Installation}

\texttt{kubectl} is the client. It talks to a cluster you already have, so
installing it does not give you Kubernetes; for a local cluster use Docker
Desktop's built-in one, or \texttt{kind}, \texttt{k3d} or \texttt{minikube}.

\begin{sh}
# Windows
winget install Kubernetes.kubectl
# macOS
brew install kubectl
# Linux -- pinned to the current stable release
curl -LO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
\end{sh}

\field{Verify:}{\texttt{kubectl version -{}-client} prints the client version
without needing a cluster. Drop \texttt{-{}-client} to check the connection as
well; \texttt{kubectl cluster-info} is the fuller answer.}

\section{Helm}

Helm is the package manager for Kubernetes. It installs and manages applications
packaged as charts, the way \texttt{apt} installs packages on Debian.

\subsection{Installation}

\section{Terraform}

Terraform builds cloud infrastructure from code. Instead of clicking through an AWS,
GCP or Azure console, servers and services are declared in configuration files and
Terraform reconciles reality with them.

\subsection{Installation}

\begin{sh}
# Windows
winget install HashiCorp.Terraform
# macOS
brew install hashicorp/tap/terraform
# Linux (Debian/Ubuntu) -- the HashiCorp apt repository
wget -O- https://apt.releases.hashicorp.com/gpg | \
  sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] \
  https://apt.releases.hashicorp.com $(lsb_release -cs) main" | \
  sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt update && sudo apt install terraform
\end{sh}

On the RHEL family use \texttt{dnf config-manager} against
\texttt{https://rpm.releases.hashicorp.com} instead.

\field{Verify:}{\texttt{terraform -version} prints the version and warns when a
newer one is out. Terraform needs no daemon, but every provider it uses is
downloaded on \texttt{terraform init}, so that is the command that first needs
network access.}

\subsection{Commands}

\begin{cmdtable}[4.8cm]
terraform -{}-help & Display general help for the Terraform CLI \nr
terraform init & Initialise the working directory and download the provider plugins the configuration needs \nr
terraform validate & Check the configuration files for syntax errors and internal inconsistencies \nr
terraform plan & Produce an execution plan showing what Terraform will do to reach the desired state \nr
terraform apply & Apply the changes required to reach the desired state, prompting for approval first \nr
terraform show & Display the state, or a saved plan, in human-readable form \nr
terraform output & Display the output values defined in the configuration \nr
terraform destroy & Destroy the infrastructure the configuration manages, prompting for confirmation \nr
terraform refresh & Update the state file from the real infrastructure without applying any change \nr
terraform taint & Mark a resource for recreation on the next apply, even if nothing about it changed \nr
terraform untaint & Remove the tainted status from a resource \nr
terraform state & Manage the state file: move resources between modules, remove them, inspect them \nr
terraform state list & List every resource tracked in the state file \nr
terraform import & Bring existing infrastructure under Terraform management \nr
terraform graph & Generate a graph of the resources and their dependencies \nr
terraform providers & List the providers the current configuration requires \\
\end{cmdtable}

\field{On the backend:}{The backend is configured in a \texttt{backend} block inside
\texttt{terraform \{ \}}, not from the command line. It decides where the state file lives:
locally by default, or remotely in S3, Azure Blob Storage, Terraform Cloud and others.
\texttt{terraform init} is what reads it and migrates existing state.}
